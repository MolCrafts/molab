# CLAUDE.md

molab is a scientific-workflow platform for FAIR research — Python (FastAPI + a self-owned workflow engine) + TypeScript/React 19 UI, shipped as one wheel.

## Where things live

- Python source: `src/molab/` · TS source: `apps/web/src/` (VS Code ext: `apps/vsc-ext/`)
- Tests mirror source: `tests/` ↔ `src/molab/`, `apps/web/src/` for the web UI
- Public docs: `docs/` · in-flight specs: `.claude/specs/` (gitignored)
- **Detailed module map: `.claude/notes/architecture.md`** — keep that file as the index; CLAUDE.md only carries invariants

## Hard invariants (do not change casually)

- **One home per fact.** Each persisted fact has one canonical file. Everything else is rebuilt on read, or is a cache under `.molab/` that can be deleted whole.
- **References are ids, not paths.** A cross-subsystem reference is a `molab:` ref built by `molab.workspace.refs` (`MolabRef` / `parse_ref` / `REF_SCHEME` / `is_ref` / `ref_of`). No path is parsed back into an identity. A knowledge document's path is its identity, and that is the only exception.
- **The owner writes; everyone else asks.** Workspace writes entity JSON and `execution.json` (a legacy attempt is folded by `execution_repository.fold_legacy_attempt`, D66), a Folder's `index.md` narrative, and artifact and asset bytes. Workflow writes the journal and the node-cache contents. Knowledge writes knowledge documents (`<host>/knowledges/*.md`). **The one named exception (D74):** the offline, one-shot migrator `molab migrate layout` still writes the migrated `run.json` / `experiment.json` / `project.json` / `workspace.json` directly, via `_stamp` and `_write_json`. That debt is recorded in `.claude/notes/open-questions.md` (fold those records through the owner, the way `fold_legacy_attempt` does). The other `molab migrate *` commands (`assets`, `workflow-kind`, `knowledge`, `brand`) only move bytes or call an owner function.
- **Only a public contract crosses a subsystem.** Workflow and knowledge do not import a workspace name that starts with `_`, and they do not assemble a workspace path. Workspace never imports workflow or knowledge, and it carries no knowledge vocabulary. Workspace does own `bind_workflow`, the `workflow_kind` association, and the `set_run_executor` seam; those are not a leak.
- **Executions are append-only.** A record starts from QUEUED once, inside `ExecutionRepository.start`. After seal the record is immutable. The only post-seal field set is `pruned_at` / `pruned_dirs`, written only by `mark_pruned`. Prune keeps the record, and an `eNN` id is never reused. Resume always creates a new derived Execution.
- **Provenance before work; history after the write.** Creation-time facts land in the record before the job is submitted, and start-time facts land before the first task. The git commit follows the files it describes and never blocks the science.
- **Only the owner mints an id.** Workspace allocates entity ids, `eNN`, and artifact and asset ids. A new workspace's `workspace.json` id is a UUIDv7 minted only for a new workspace, persisted create-if-absent at `materialize` (a handle that finds `workspace.json` already written adopts the id on disk) and never rewritten afterwards. A legacy slug id is kept (D75). Workflow computes `workflow_digest`.
- **A cache is keyed by identity and covers every input.** The node cache lives at `run.machine_dir() / "cache"`, which is `.molab/runs/<run-id>/cache/`. The key covers the snapshot, the inputs, and the effective config.

- **MolRec layering:** molrec is a **protocol**, not a library — follow it by convention; **never `import molrec` in production** (a conformance suite, if added, is a test-only extra). A molab **Run is a host**, not a MolRec record (`run.json` + run-root `alive` ≠ molrec `meta` / `status`). Scientific packages follow the external spec (Zarr root). **Nobody owns a format except the package that can parse it.** molrs owns the solver formats; molplot displays and **registers no reader**, molab ships none either. **The frontend never asks Python about a format.** The server is a filesystem to it: list an attempt's files, hand back bytes. Everything else — which file is plottable, what the numbers mean — is decided in the browser by a `MetricReaderContribution` (`format` / `patterns` / `claims(text)` / `read(source, request)`) contributed by `plugins/molrs`, which parses via **molrs-wasm**. A chart therefore comes straight from `log.lammps` with no server-side parsing, and adding a format needs no server change. There is no `/molplot` read route and no format endpoint; `molplot/ingest` (persist to the WAL) is the only server-side format path that remains. `@molcrafts/molrs` is imported **only** through `lib/molrs.ts` (one WASM instance; no plugin depends on another) and every export is feature-detected, so a binding that predates an export disables that format instead of crashing. Nothing is privileged — molab's own `*.mlp.jsonl` is contributed like any other format. **The viewer sets the resolution, in simulation steps**: molplot passes `MetricReadRequest.stepInterval` ("a point every 10 000 steps") and each reader thins **per series** on the step axis. Never per row — a solver's thermo frequency changes between restart blocks (a real run here writes every 576-1000 steps), so every Nth row samples one stretch of a run denser than another, and the viewer would have to know a row count it cannot know. A record with no step is a one-off scalar and is always kept. Readers cache parsed tables by `path@revision` so a re-read re-slices instead of re-parsing. Server-side, the same formats reach `ingest_run` through the `molcrafts.metric_readers` entry-point group (molpy → molrs-python) — one Rust parser, two bindings, never two implementations. `molab.plugins.metrics` still owns the *writing* surface (`out/<stem>.mlp.jsonl` WAL) through the `workspace.metrics_seam` inversion seam; ingest persists reader output there and is always **optional**, and must exclude its own destination or it reads the file it is appending to. Conventions live in molab / molvis / molplot products, not UI-plugin patches. **Charts: molplot only** — molvis opens structures (PDB / XYZ / dumps / `*.mrec` Zarr) and claims no solver log, so no file is offered behind two tabs one of which cannot draw it. There is no server-side log parser either: the `lammps-log` route and its `LammpsLogResponse` schema are gone, because a regex in a FastAPI handler is a second implementation of a format molrs already owns.
- **Extension points.** Third-party packages attach through entry points — molab.cli_plugins / molab.server_plugins / molab.ui_plugins — and molab ships none:
  - **CLI** — a `molab.cli_plugins` entry point names a CLI plugin object. A plugin attaches to the app it is handed and **never reaches into another package's command tree**.
  - **Server** — a `molab.server_plugins` entry point names a server plugin (`register` / `startup` / `signal_shutdown` / `shutdown`). Same process, same port, same session cookie; `create_app` never names a route module it does not own. **A plugin owns its wire**: its request/response models live in its own package, not in molab's `server/schemas/`.
  - **UI** — a `molab.ui_plugins` entry point names a UI bundle (served from `/api/plugins/{id}`).
  - **Inversion seams** — a lower layer exposes a registration function and a higher layer (or the layer itself, lazily) installs the implementation, so no arrow of the Layer DAG is reversed: `molab.workspace.run.set_run_executor` (`Run.execute` / `RunSet.execute` / `Run.get_result`; `molab/__init__` registers a lazy proxy that loads `molab.workflow` on first call), `molab.workspace.metrics_seam` (`set_metrics_writer_factory`; `molab.plugins.metrics` registers the metrics WAL writer at `import molab`), `molab.workspace.experiment.set_workflow_executor` (`Experiment.run`; wired at `molab/entry.py` to `_execute_experiment`), Knowledge registers no concept-created hook; that module was removed.
  - **Named exception (D-1, drop-harness):** molab registers nothing in `molab.cli_plugins` / `molab.server_plugins` after D86; the channels are kept by user decision as public extension points (exercised by `tests/test_plugins/test_cli_discovery.py` / `test_server_discovery.py`), an explicit exception to "No speculative code in `src/`".
- **Layer DAG** (enforced by `tests/test_<layer>/test_import_guard.py`): `services → workflow + workspace`, `workflow → workspace`, and `knowledge → workspace` — the last **one-way and function-body only**. `molab.services` (`operator_config` / `run_failure` / `auth`) sits below CLI/server — CLI and server import services, never each other. Any other arrow is an architectural defect.
  - **Named debt (drop-harness review):** "Python 操作 = UI 操作" is not yet true for two run verbs. The server's cancel route (`server/routes/run.py` `cancel_execution`) is a separate implementation from `molab.workspace.lifecycle_ops.cancel_run`, and no prune route exists for `molab.workspace.prune` (`plan_execution_prune` / `apply_execution_prune`). Fold the route onto `cancel_run` and add a prune route rather than growing a third path.
- **Workflow public API**: decorator and OOP styles on `Workflow`; `WorkflowCompiler().compile(workflow)` produces the frozen `CompiledWorkflow`. Never mix them: `Workflow` is the authored graph (no `.compile()`), `WorkflowCompiler` is not a builder (`WorkflowCompiler(name=…)` is gone). Task bodies may be plain `def` **or** `async def` (sync bodies run via `asyncio.to_thread`, never blocking same-level parallelism). `Workflow` / `WorkflowCompiler` / `TaskContext` / `WorkflowRuntime` are re-exported lazily at the top level (`molab.WorkflowCompiler`, …) — `import molab` must stay light (no `pydantic_graph` in `sys.modules`; the dependency itself was removed).
- **Interface naming contracts (frozen — reject new spellings).** `params` is the one kwarg spelling across the hierarchy (`add_experiment(params=…)` / `add_run(params=…)` / `run(wf, params=…)`). `cancel` is the stop verb (see verb law); the operator config file is `~/.molab/config.json` (`services/operator_config.py`: load / save / set — CLI, server and `services.auth` share one loader, the CLI (`molab config set`) is its only writer, and nothing is copied into `molab.config`). Knowledge documents use `write` / `read` (not `set_body` / `body` / `write_head`). Run working paths: `run.path` (alias `run.run_dir`) is the run root as `pathlib.Path`; `workdir` is the current context's scratch (`RunContext.workdir` / `TaskContext.workdir`) — never `work_dir`. The disk is `workspace.fs` (`FileSystem`: local / remote / cached) — Folders do not own a filesystem. User byte writes go through `folder.files` (`FileStore` rooted at that folder). Run identity (`run.json`) holds only the logical definition (params / `definition_hash` / revision links); hot state and results live in the per-attempt `executions/eNN/execution.json` (`Execution`), and the owner heartbeat is the mtime of the per-Execution `alive` file (missing is not stale). Framework byte writes under an attempt go through one `FileStore`: `ctx.files.put` / `append` (atomic via `molab.atomicio`) writes into `executions/eNN/work/`, the framework's scratch tier (`ExecutionContext.files`, `execution_dirs.WORK`); task products land in `executions/eNN/out/<task>/` through `TaskContext.workdir`; `run.json` and `executions/eNN/workflow.json` / `execution.json` are written atomically via `molab.atomicio`. Catalog rows are orthogonal (`ctx.register(path, kind=…)`); `register_artifact` is the compose of put-into-`executions/eNN/out/` + register. Cache stores return JSON + content-addressed blobs under `.molab/runs/<run-id>/cache/`, never writes `out/` itself. Query the catalog with `{scope}.assets`; import external data with `{scope}.data_assets.import_asset`. Do not add `ctx.artifact.save`, `ctx.folder`, `register_asset`, or `reregister_artifact`.
- **`Workspace → Project → Experiment → Run` is a `Folder` family.** Generic CRUD (`add_folder / get_folder / has_folder / list_folders / remove_folder`) + typed semantic sugar per subclass (`add_project / add_experiment / add_run / …`). **There are no children-index files** — the directory tree *is* the index, so `list_folders` scans the container and nothing can drift from disk. `get_folder` / `has_folder` / `remove_folder` accept a directory name, a display name, or the entity's id. `add_project` / `add_experiment` are idempotent on display name; `add_run` is idempotent only on an explicit `id=` — every other call allocates a fresh run.
- **OpenAPI surface** under `src/molab/server/routes/`; the web UI regenerates against it (repo root: `npm run generate:api`). Don't hand-edit `apps/web/src/api/generated/`.
- **Private subpackages** — never import from outside their owning layer: `workflow/_engine/` (the self-owned execution engine).
- **The self-owned engine and molq are evaluated decisions, not defaults.** Temporal / Ray / AiiDA / PSI/J were each assessed against source and release data and rejected as replacements (they lose on the one-source-of-truth law and on one-wheel distribution). Standing verdicts stay inline: those engines lose on the one-source-of-truth law and on one-wheel distribution. The evidence file is missing; that gap is recorded in `.claude/notes/open-questions.md`.

## Architecture

```
  third-party plugins     molab.cli_plugins / molab.server_plugins / molab.ui_plugins
    │                      entry points (molab ships none — D-1)
    ↓
  molab                   the scientific-workflow platform
    ├─ cli, server         application shells
    ├─ services            operator_config / run_failure / auth
    ├─ workflow ─→ workspace
    └─ knowledge ─→ workspace
```

molab's Server + CLI sit on top of **`molab.services`** (the application-service layer: `operator_config` / `run_failure` / `auth` — one backend code path for "Python 操作 = UI 操作"). UI is downstream of the server's OpenAPI. Cross-layer primitives (`molab.path`, `molab.profile`, `molab.entry`, `molab.atomicio`, `molab.ids`, …) sit above workspace and may be cited from any layer. **`molab.knowledge`** sits just above `workspace`: it owns the OKF storage substrate (a document is a directory, or a `knowledges/<slug>.md` file, whose path is its identity) Documents are `<host>/knowledges/<slug>.md` files. **`molab.knowledge` depends on `molab.workspace` (function-body imports only); `molab.workspace` must not import `molab.knowledge` at all.** `molab.config` is the process-global in-code config — a live `molcfg.Config` instance defined in `molab/__init__.py`, never read from env. **Named exception (D-2, drop-harness):** it is kept by user decision although no molab module reads it after D86, an explicit exception to "No speculative code in `src/`". `molab.profile` is the separate file-based, per-run profile config (`ProfileConfig` / `MolCfg` / `load_molcfg`).

### Layer charters

**`molab.fs`** — layer-0 primitive; the filesystem seam, shared by `workspace` and `knowledge`.
- Owns the `FileSystem` Protocol + `PathArg` / `StatResult` / `DirEntry` (`base.py`), the single `LocalFileSystem` (`local.py`), and `memo.py` (`StatMemo`) / `profile.py` (`FsProfile` / `detect_fs_profile`) / `window.py` (`read_text_window`). `fs_remote` / `fs_cached` stay in `workspace` — they bind `molq`, and keeping them there is what makes `import molab.fs` stdlib-only (locked by `tests/test_fs/test_import_weight.py`); every module added here stays stdlib-only too.
- **One** `LocalFileSystem` class, re-exported by `workspace/{fs,fs_local,gitignore}.py` as the *same object*. This is load-bearing: `Folder.move_to` gates on `isinstance(self._fs, LocalFileSystem)`, so a second parallel class would make that check silently False on a perfectly local tree.
- **`scandir` and `read_range` are required Protocol members**, not optional accelerators: `scandir(path, *, with_stat=True)` answers name+type+size+mtime in one syscall / round-trip, and `read_range(path, offset, length)` reads a window. Every implementer (Local, Remote, Cached, and every test fake) implements both. A walker reaching for `listdir` + per-entry `is_dir`, or a reader slurping a whole file to show its tail, is the bug pattern this exists to prevent.

**`molab.knowledge`** — just above `workspace`: file documents under each host; it reaches `workspace` only through function-body imports.
- **A knowledge document is `<host>/knowledges/<slug>.md`.** Path is identity. Frontmatter carries `class:`. Typed links are `[@role label](target)`. A host is the workspace root, a project, an experiment, or a run. Reconstruction is `Knowledge.open(path)`. User verbs: `write` / `read` / `rename` / `move_to` / `delete` / `backlinks` / `export`. `write_knowledge` is the only create path. The single layout literal is `KNOWLEDGE_CONTAINER`. Knowledge never spells the `molab:` scheme.
- **Six subclasses of `Knowledge`:** `Note`, `Literature`, `Report`, `Finding`, `Plan`, `Observation`. Failure analysis is a `Report`; harvest of a scientific outcome is a `Finding`. Harvest targets are the subset Finding / Observation / Report.
- Owns: `concept.py`, `concepts.py` (the six classes), `write.py` (`write_knowledge` / `mount_note`), `search.py` (BM25F), `sources.py`, `edges.py`, `retrieval.py`, `zotero.py`, `location.py`. Does not own workspace storage, workflow execution, or asset bytes.
- **Knowledge is not a Folder.** Workspace `Folder` subclasses compose a path from a parent chain; `Knowledge` *is* its path. Knowledge writes itself as `<host>/knowledges/<slug>.md`.
- **Retrieval is keyword ranking, not RAG.** BM25F over title/tags/path/body; CJK runs emit unigrams **and** adjacent bigrams so IDF self-balances — no segmenter, no dictionary, no embeddings.
- **A read never writes.** `search()` and the scans build the index in memory and return it.
- **Allowed imports**: stdlib, pydantic, pathspec and the layer-0 primitives `molab.fs` / `molab.gitignore` / `molab.ids` / `molab.path` / `molab.atomicio` / `molab._typing`. **`molab.workspace` may be imported only inside a function body** (or a `TYPE_CHECKING` block); importing `workflow` / `services` / `server` / `cli` / `plugins` is banned at **any** scope — enforced by `tests/test_knowledge/test_import_guard.py`, an **AST source scan** (not a `sys.modules` probe: `molab/__init__.py` eagerly loads `workspace`, so a runtime probe is unsatisfiable).

**`molab.workspace`** — bottom; pure storage.
- Owns: `Folder` base + the `Workspace/Project/Experiment/Run` subclasses, typed exceptions (`*NotFoundError` / `*ExistsError`), atomic JSON I/O (`atomic_write_json`), the `Asset` family (`asset.json` + `versions/vNNN.json` at workspace, project, and experiment scope; `AssetRepository`), `Params` / `ParamSpace` / `GridSpace` / `UniformSpace`, the **unified Target family** (`ComputeTarget` is the persisted base; `LocalTarget` / `RemoteTarget` are its address-view subclasses; `resolve_compute_target` is the single named-target resolution path for CLI and server; `SSHSession` for transport caching), `RunContext`, `RunSet` / `RunSetResult` (sweep container: `experiment.sweep(...)` → `runset.execute()` → `to_records()` / `min_by()`; execution delegates through the `set_run_executor` inversion seam so workspace never imports workflow), zombie reaping (`run_reaper.reap_zombie_run`, called by every CLI **and** server verb entry), run-lifecycle verb cores (`lifecycle_ops.cancel_run`; two-phase `prune.plan_execution_prune` / `apply_execution_prune`), Execution auto-cache writes `.molab/runs/<run-id>/cache/`. **There is no derived asset index** — asset reads go through `AssetRepository`, and emitted products are read from the Executions that own them (`artifact_repository.scan_artifacts`). Unmigrated asset records raise `UnmigratedAssetError` (HTTP 409 `MIGRATION_REQUIRED`) until `molab migrate assets` has been run once (D83).
- **The Concept family and the mounting verbs belong to `molab.knowledge`** (`Note` / `Literature` / `Report` / `Finding` / `Plan` / `Observation`, `write_knowledge` / `mount_note` / `harvest_run`); workspace supplies the tree and the bytes and does not name knowledge. `Folder` and `Knowledge` stay **independent base classes** — a `Folder` composes its path from a parent chain, a `Knowledge` *is* its path. The legacy per-scope library was removed; greenfield, no migration.
- MUST NOT: **import, name or reference `molab.knowledge` in any form — no import (module body or function body), no identifier, no docstring or comment mention, no knowledge-named source file.** MUST NOT import any other upstream `molab` layer (`workflow` / `plugins` / `services` / `server` / `cli`). Allowed `molab.*` imports are only `_typing` / `profile` / `path` and cross-layer primitives (`mollog`, `molcfg`) — **`molab.knowledge` is not in that list and must not be added to it**. MUST NOT define workflow- or agent-shaped types. MUST NOT write to disk in `__init__` — all I/O is lazy. `Workspace.__init__` does not write `workspace.json`; `materialize` persists a new id create-if-absent.
- `import molab.workspace` must never pull `molab.workflow`, `molab.knowledge`, or `pydantic_graph` into `sys.modules`.

*Identity & persistence law (workspace).*
- **A Run's `definition_hash` has one implementation and does not name a path.** `molab.workspace.run.compute_run_definition_hash(experiment_revision_id, parameters, input_asset_ids)` is the only place a run's definition is hashed — `Experiment.add_run`, `_seed_missing_runs` and `Run.__init__` all call it (they used to hand-roll two different digest shapes, and the two doors used to fold different fields into the digest). **The workflow is the experiment's property, not the run's**: `Experiment.bind_workflow` is the only writer of `workflow_kind` (`code` or `document`) and of `workflow.ir.json` (written only by `_write_workflow_doc`). `compute_run_definition_hash` keeps the frozen hash key `"workflow_snapshot": None` so the digest stays stable (D45). A profile `config_hash` is content-only: the profile name is a label, so two profiles with the same data share one reproduced run (D51). Locked by `tests/test_workspace/test_run_identity.py`.
- **Three orthogonal id layers, no fourth.** Uniqueness → `generate_uuid7()` (time-ordered UUIDv7 for Project / Experiment / Run / Artifact; an Execution is identified run-locally as `e01` / `e02`, so `(run_id, execution_id)` is the global handle). Reproducibility & dedup → content hashes: `definition_hash` (`"sha256:…"`) is a run/experiment-revision's *one* reproducibility identity, `compute_content_hash()` addresses artifacts. Location → `AssetScope(kind+ids)` + `execution_id`. A run carries exactly one identity — never add a second parallel run-fingerprint type alongside `definition_hash`.
- **Identity is never the path.** A directory name is a *name*, for people: `experiments/<slug(name)>`, `runs/<key=value_…>` (its parameters, sorted; a digest when there are none), `executions/e01`. The UUIDv7 lives in the entity JSON's `id`, which is what cross-entity references cite — so renaming a directory breaks nothing, and `ls` tells you what was run. `molab.workspace.naming` owns every derivation. **A client therefore never composes a workspace path.** Every entity response carries `path` (`ProjectResponse` / `ExperimentResponse` / `RunResponse` / `WorkspaceRunRow`, via `schemas.responses.workspace_relative`), and `RunResponse.name` is the run's parameters; the UI reads both and derives neither, because an id-composed path names a directory that was never created.
- **Run vs Execution.** `Run` = immutable logical intent (params + workflow + revision/definition links, persisted as `run.json` = definition only); `Execution` = one physical attempt, `e01` / `e02` / …, N-per-run. **One attempt is one file**: `executions/eNN/execution.json` (`Execution`: mode, status, ownership, started/finished, executor, environment, emitted artifacts, evidence, error, seal) is the whole of it — there is no second sealed record elsewhere and no sidecar beside `execution.json`. Failure evidence is that attempt's `run.log` plus `traceback.txt`, named only by `execution_context.py`. Sealing sets `sealed_at` and freezes the terminal fields. Cross-attempt reproducibility identity stays at run level (`definition_hash`). An Execution persists completed-task outputs at **workflow-node granularity**, so a failed attempt can be resumed by creating a new Execution that seeds completed nodes.
- **Execution modes (four creation modes, all on the same `run_id`; there is NO new-Run operation).** `ExecutionMode` is `INITIAL` / `RERUN` / `RESUME` / `REPRODUCE`. `ExecutionMode.RETRY` is stored as `RERUN`; an old `"retry"` record still reads. A non-INITIAL mode defaults to the latest attempt, which must already be terminal. RESUME requires a terminal, unsuccessful predecessor; the checkpoint is optional. RERUN may follow any terminal status. REPRODUCE requires a succeeded predecessor and forces `bypass_cache`. `Run.status_label` is the latest attempt's status (`"pending"` when there is no attempt; QUEUED reads as `"queued"`). `Run.has_failures` is true when any attempt is failed, cancelled, or interrupted. `Run.is_retryable` is true when nothing is active and `has_failures` is true. So a run that fails and then resumes to success has `status_label == "succeeded"` and `has_failures is True`. Cloning params into a fresh `run_id` is NOT a molab operation. **Success requires evidence**: an attempt that runs nothing flips nothing — the sealed `Execution`'s terminal status is the engine's signal (`succeeded` / `failed` / `cancelled` / `interrupted`); a task failure is recorded on `Execution.error` and its traceback lands in that attempt's `run.log` and `traceback.txt`. `Run.create_execution` and `Run.start` (with no `execution_id`, via `ExecutionContext`) both reach `ExecutionRepository.create`, which is the only creation point for a new attempt. `Workspace.machine_dir(root)` is a staticmethod: it does not construct a `Workspace`, it ignores the CLI root override, and it does no I/O. `Workspace.find` resolves a `molab:` ref. `qualify_run_id` stays permanently as the qualifier for a legacy bare run id (D18). `Workspace.enclosing_root` and `Workspace.list_hosts` locate hosts. Container constants live in `workspace/naming.py`. An artifact path is unique within one attempt: emitting a recorded relative path again raises `ValueError` (Q3). `artifacts/_molab/results.json` is the reserved result artifact, written when the context exits. A captured source snapshot lives at `executions/eNN/source/`.
- **Run status is derived, not scalar.** A `Run` has no scalar `status`; callers read `run.status_summary` (a `RunStatusSummary`: total/active/not_started/by_status) or `run.executions` (ordered `Execution`s). `Run.is_retryable` is true when any Execution is terminal `failed`/`cancelled`/`interrupted`. `cancel` targets one active Execution id (`run.cancel(execution_id)`) — a Run itself is not scalar-cancellable. A stale `running` Execution is reaped to `failed` *before* any verb decides — same-host with a dead owner PID, or **cross-host only when the per-Execution `alive` exists and its mtime is older than 600 s** (touched every 30 s by the owner; missing `alive` is not stale — a live HPC job that has not claimed yet). CLI / server / the Python one-step API (`execution.execute(wf)` / `run.execute(wf)` / `RunSet.execute`) share the same Execution-mode path via `ExecutionRepository`; the CLI noun group stays plural (`molab runs …`) deliberately (typer's flat per-level namespace means a `run` group would shadow the top-level `molab run` verb).
- **One source of truth — and it is the files.** Entity `*.json` files and each asset's `asset.json` are authoritative. There is **no** second store to reconcile. A query is a walk of the tree (`list_folders`, `AssetRepository`, `artifact_repository.scan_artifacts`). Never add a file whose only content is a copy of something already on disk.
- **History is git.** The workspace is a git repository; every mutation ends in a commit whose message trailers carry the typed fact (`Molab-Event` / `-Subject` / `-Agent` / `-Rel` / `-At`), so `git log` is the provenance query and `git push` is the backup. `molab.workspace.GitHistory` owns it, `molab history {log,init,sync,push}` is the CLI. History is a **soft** dependency: nothing reads it to answer an operational question, and a worker that cannot take the commit lock leaves its files for the next commit — science never blocks on git.
- **An attempt's directories are peers, and their meaning is data.** `molab.workspace.execution_dirs` declares each one (`ExecutionDir`: `name` / `purpose` / `versioned` / `products`) and **every** question about them is a query, never a string match: the workspace `.gitignore` is generated from `versioned`, the metrics WAL searches `products`, the layout validator's legal-name set is `execution_dir_names()`. Three tiers — `work/` (framework scratch: `ctx.files`, emit staging), `out/` (**where a workflow task writes**: `ctx.task_workdir(t)` / `TaskContext.workdir` is `out/<task>/`; bulk, kept on disk, gitignored), `artifacts/` (promoted, registered, versioned) — plus `jobs/` and `checkpoints/`. A task body's output is genuinely mixed (its generated inputs, its intermediates, its trajectory) and cannot be sorted from outside, so it lands in the tier that is *kept*, never the disposable one; `register_artifact` / `emit_artifact` then promotes anything citable into `artifacts/` from **any** tier. Bulk stays out of git by file-type patterns regardless of tier, so a trajectory promoted into `artifacts/` is still not committed. One accessor reaches all of them — `ctx.get_dir(name, *parts)` / `has_dir` / `list_dirs`; there is **no** per-directory property (`ctx.workdir` is gone, and `PRODUCTS_DIR` with it), and an undeclared name raises `UnknownExecutionDirError` rather than creating a directory nothing validates. Registration is open, so a package declares the directory it writes. The server ships the declarations on `RunFilesResponse.dirs`, which is how the UI knows a `.mlp.jsonl` under `products` is a result and the same name under scratch is not — **the frontend never infers a directory's meaning from its name**. `TaskContext.workdir` keeps its name (frozen; the engine canonicalises it out of the cache key and it may be `None` off-workspace) — it is the *role* name for where a task works, and the directory it resolves to is `out/<task>/`.
- **Machine state lives in `.molab/`.** Locks, the workflow node cache, anything a person never opens. A scientific directory contains science. `.molab/` is gitignored and can be deleted whole.
- **No speculative code in `src/`.** A subsystem with zero production callers does not ship. "Future" capability with no live call-path belongs in docs or a branch, not the tree.

**`molab.workflow`** — middle; graph execution engine.
- Owns: `Workflow` (decorator + OOP, mutable) → `WorkflowCompiler().compile(workflow)` → `CompiledWorkflow` (frozen, content-hashed). `Task` / `Actor` convenience bases; user-facing protocols are `Runnable` / `Streamable`; task bodies may be sync or async. `TaskContext` (the single context for batch + streaming bodies), `TaskTypeRegistry`, `TaskSnapshot` (AST-normalized hash), `Caching` (LRU), `WorkflowResult` / `WorkflowExecution` (result-level status vocabulary is `succeeded`/`failed`; legacy persisted `"completed"` is normalized on read), `End` (molab-owned sentinel in `workflow/types.py` — generic frozen dataclass, `End()` / `End(data)`; defined exactly once), `Next` (routing return value for `wf.branch` / `wf.loop`), `promote_callable()`, and `Execution.execute` / `Execution.aexecute` (one-step tracked execution of one attempt + the `RunFailedError` / `RunNotExecutableError` pair; `run.execute` / `RunSet.execute` reach that path through the `set_run_executor` seam). Private `_engine/` is the self-owned execution engine — **pydantic_graph is no longer a dependency and must not be imported anywhere in `src/`** (enforced by `tests/test_workflow/test_engine_boundary.py`, a full-src AST scan).
- Uses workspace: `Workflow.execute(run=…)` takes a `workspace.Run`; `Caching` is backed by `.molab/runs/<run-id>/cache/` (auto from `RunContext`) or an explicit `CacheStore`; run-state JSON writes go through `workspace.atomic_write_json`.
- **resume is task-granular, caller-driven, and self-validating.** A failed run preserves completed outputs in `WorkflowResult.outputs`; the caller (CLI/server) re-seeds them via `runtime.execute(..., seed_outputs=…)`, sourced from the *existing* execution's persisted node-level state. Node state is persisted **incrementally** to `executions/eNN/workflow.json` (per-task status + outputs + `snapshot_key` + `outputs_lossy` flag — not per-frame engine checkpoints; within-task checkpointing belongs to `ctx.workdir`). At seed time the engine drops (warn, recompute — never error) any seed whose recomputed `TaskSnapshot.key` differs (code changed), whose outputs were lossy-truncated, or which cannot be verified (pre-flag documents). Seeded nodes are recorded in `WorkflowState.seeded` and skip their body (`from_seed`); unknown seed names fail-fast. `rerun` simply calls `execute` with no seed (new `exec_id`). SubWorkflow inner runs execute with persistence off — `executions/eNN/workflow.json` always describes the **outer** graph only.
- MUST NOT: import `plugins` / `server` / `cli` / `services`. MUST NOT import `pydantic_graph` anywhere (the dependency is removed). No second `End` sentinel (single definition in `types.py`), no per-task node-class codegen. `Next` is public (the `wf.branch` / `wf.loop` routing return value, in `molab.workflow.__all__`) but stays out of the frozen top-level `molab.__all__` / lazy re-exports.
- **Identity and resume.** `compute_workflow_digest` / `CompiledWorkflow.workflow_digest`. The digest has two homes: `Execution.workflow_digest` and the journal header of `executions/eNN/workflow.json` (`workflow_digest`, `workflow_name`, `based_on_execution_id`; no top-level status). Readers are `read_journal`, `read_outputs`, and `read_resume_seeds`. The only resolution path is `molab.workflow.recovery.compiled_workflow_for_run` / `compiled_workflow_for_experiment`. `load_workflow_from_entrypoint` is exported only from `molab.workflow` (defined in `molab.workflow.loader`); `molab.entry` does not re-export it (D82). `execute_run(..., execution_id=)` is the only execution path. `workspace_run_executor()` is what the lazy `set_run_executor` seam installs. `Run.execute` and `RunSet.execute` do not pass `execution_id` or `profile_config` through (D65: no caller, a decision, not a debt). The authoring `remote=` kwarg on `WorkflowCompiler`, the declarative graph, and `CompiledWorkflow` is removed, and `WorkflowRuntime.execute` / `start` no longer take `run_dir=` (D82). There is no `plan_execution_id`; `plan_run_id` is a read-only legacy field and is not written.
- **A stuck QUEUED attempt.** Submit creates the QUEUED `eNN` before submit and stages `executions/<id>/`. If the scheduler job dies before the worker starts and a terminal event is observed, the record is sealed with error type `SchedulerJobEndedBeforeStart`. If no event is observed, the record stays QUEUED. The remedy is `molab runs cancel <run-id>…` (run ids, or `--project` / `--experiment` with `--all` / `--status`), which cancels each run's active attempt, QUEUED included. The Python call is `run.cancel("eNN")`. A scheduler RESUME on a remote target recomputes, because the predecessor journal is not staged. Upgrade commands are `molab migrate assets`, `molab migrate workflow-kind`, and `molab migrate knowledge`.

**`molab.services`** — application-service layer between CLI/server and the domain layers.
- Owns: `operator_config` (the `~/.molab/config.json` file loader and writer — load / save / set; CLI, server and `auth` read through it, only the CLI writes), `run_failure`, `auth` (filesystem users + sessions for `molab serve`), `workflow_kind` (D20), `knowledge_context`, and `copilot` (06f). This is where "Python 操作 = UI 操作" is enforced: CLI commands and server routes both call services, never each other.
- Uses: workflow, workspace. MUST NOT: import `server` / `cli` / `plugins` — enforced by `tests/test_services/test_import_guard.py` (AST scan); every lower layer's guard forbids importing `services` back.

## On-disk layout

This layout is the **authoritative experiment-directory spec** — the shape any tool restructuring data into a molab workspace must produce. The directory tree is the only child index. Per-attempt artifacts live under `executions/<exec_id>/`; cross-attempt state stays at the run level. Asset records are `asset.json` plus `versions/` under the owning host.

```
workspace_root/
├── .git/                         # the history: one commit per fact (molab history log)
├── .gitignore                    # bulk payload is reproduced, not versioned
├── .molab/                      # machine-only; deletable; never opened by a person
│   ├── locks/                    #   advisory locks (run, execution, history, assets)
│   └── runs/<run-id>/cache/      #   workflow node cache, per run (`run.machine_dir()`)
├── workspace.json                # workspace ENTITY + OKF type (workspace.root)
├── index.md                      # OKF narrative; its markdown links ARE the knowledge graph
└── projects/<project-slug>/      # container "projects/", dir name = slug(project name)
    ├── project.json              # project ENTITY metadata (singular; holds the UUIDv7 `id`)
    ├── knowledges/tg-cooling.md  # knowledge document (frontmatter class + markdown)
    └── experiments/<experiment-slug>/     # dir name = slug(experiment name)
        ├── experiment.json       # experiment ENTITY metadata (singular)
        ├── workflow.py           # the experiment's own script, beside the runs it produced
        ├── knowledges/tg-cooling.md  # same file shape as the project-level document
        └── runs/<dp=5_seed=42>/  # dir name = the run's parameters, sorted (digest when there are none)
            ├── run.json          # logical definition only (params / definition_hash / revision links)
            │                     # legacy dirs from pre-drop-harness runs (`harness/`, `plan/`, `approvals.jsonl`, `events.jsonl`, agent session dirs) are tolerated on read, never written
            └── executions/e01/   # one attempt; `e01` IS its id, and the id is never reused
                ├── execution.json  # THE attempt: status/ownership/executor/environment/
                │                   #   artifacts/evidence/error/seal — nothing else, nowhere else
                ├── alive           # empty file; owner heartbeat is mtime (missing ≠ stale)
                ├── workflow.json   # per-node journal (header holds workflow_digest)
                ├── run.log         # the attempt's log
                ├── traceback.txt   # failure traceback, beside run.log
                ├── source/         # captured entrypoint + first-party imports
                ├── artifacts/      # promoted + registered: metrics.mlp.jsonl, tg_fit.png
                ├── out/<task>/     # what each task wrote: trajectories, restarts, logs
                ├── jobs/<job>.{sh,out,err}   # scheduler evidence, flat — no dir per job
                ├── checkpoints/    # ctx.checkpoint payloads
                └── work/           # framework scratch: ctx.files, emit staging; disposable
```

**Layout naming law (frozen).** Each `Folder` level obeys three derivations, all driven off the class hierarchy `Workspace → Project → Experiment → Run`:
- **Container subdir** holding a level's children is the child kind pluralized: `projects/`, `experiments/`, `runs/`, `knowledges/` (Knowledge family at project and experiment).
- **Directory name** within that container is a *name a person reads*, derived in `molab.workspace.naming`: `entity_slug(name)` for Project/Experiment, `run_slug(params)` for a Run (`dp=5_seed=42`; a digest of `definition_hash` when there are no params), `execution_slug(seq)` for an attempt (`e01`). No prefixes. Collisions get a `-2` suffix. The UUIDv7 identity lives in the entity JSON's `id` and never appears in a path.
- **Entity metadata filename** at a level is the level's own class name snake_case + `.json` (**singular**: `workspace.json` / `project.json` / `experiment.json` / `run.json`). Knowledge is a markdown file, not one of those JSON heads.
- **There is no children-index filename.** A parent's children are its entity subdirectories; `ls` is `list_folders`.

The entity `*.json` files are the whole truth. History is the workspace's git log (`molab.workspace.GitHistory`), which records each fact in commit-message trailers and is never read to answer an operational question. A Run is immutable scientific intent (`run.json` = logical definition only); everything about one attempt — status, ownership, executor, environment, emitted artifacts, evidence, error, seal — is in that attempt's single `executions/eNN/execution.json`, and the owner heartbeat is the mtime of the per-Execution `alive` file.

Restructuring an older workspace into this layout is `molab migrate layout <old> <new>` (`cli/migrate_cmd.py`): it renames every directory, folds each attempt's sidecars into one `execution.json`, drops what was only a copy, hard-links bulk payload, and commits the result. Renaming machine dirs after the molexp→molab cut is `molab migrate brand`.
## Packaging

Python install and UI compile are **separate jobs**. Default `pip` / `uv pip` / `python -m build` **never** invoke npm.

- **Daily (checkout):** `molab serve --dev -ws ./lab` — open the printed **Dev UI** (`:5173`), not the API port. That starts `npm run dev:api` (real `/api` proxy). `npm run dev:web` is the MSW mock, not this path.
- **Bundled preview:** `npm run build:web` then `molab serve -ws ./lab` — open `:8000`. Editable installs read in-tree `src/molab/dist/`; **do not reinstall Python**.
- **Wheel:** `uv pip install . -C build-web=true` (never `-C build-ui=true` / `npm run build:ui`). Empty `dist/` → API-only.

```
apps/web/src/  →  npm run build:web  →  src/molab/dist/  →  setuptools  →  wheel
```

`src/molab/dist/` is gitignored (except `.gitkeep`); `create_app()` locates it via `importlib.resources.files("molab") / "dist"`. Command table: `.claude/notes/ui-serve.md`. Public: `docs/en/development/ui-serve.md`.

**UI component library:** prefer **shadcn/ui** when building UI features; if a shadcn component doesn't fit, document the reason in the PR description.

**UI server state:** **TanStack Query v5 is the only server-state cache.** The client factory is `apps/web/src/lib/query-client.ts` (`createAppQueryClient`). Query keys live with their domain: `apps/web/src/app/state/entityQueries.ts` (`projectKeys` / `assetKeys` / `runKeys`), `apps/web/src/plugins/knowledge/queries.ts`, and `apps/web/src/app/approvals/queries.ts`. A mutation calls `queryClient.invalidateQueries` for the keys it changed. A component does not fetch in a `useEffect` and does not keep server data in `useState`. Polling is a fallback for when the SSE change stream is down, gated on data (a terminal run stops its own interval) and never runs on a hidden tab. `zustand` is installed but unused — do not reach for it for server state.

## Data type ownership

Each conceptual data category lives in exactly **one** layer. Cross-layer references flow downward through the public surface of the lower layer — `workflow` imports `workspace.Run` is fine; `workspace` importing `workflow.Workflow` is forbidden. For the full ownership table (concept → owning module) see `.claude/notes/architecture.md`.

**Pydantic vs plain class.** Pure data types (events, configs, results, lineage records, IR nodes) are `pydantic.BaseModel(frozen=True)`. Runtime containers carrying live instances (callables, asyncio objects, services) are plain Python classes with explicit `__init__`.

## Key patterns

- **Topology-driven parallelism** — tasks grouped into levels by the dependency graph; same-level tasks run in parallel automatically.
- **Content-addressed caching** — `cache_key = f(snapshot.key, inputs_hash)` where `snapshot.key == f"{code_hash}:{config_hash}"` (`TaskSnapshot` — AST-normalized code + config; **inputs never fold into the snapshot**) and `inputs_hash` is owned by `Caching` (JSON-canonical over the task `inputs` channel: upstream outputs, sweep params, the effective config (profile data + `dependent_params` overlay; the profile name is a label and stays out), a stable serialization of the task output directory). Execution location is not task identity. Two sweep runs with different params never share a root-task cache entry. Auto-backed by `run.machine_dir() / "cache"` = `<workspace>/.molab/runs/<run-id>/cache/`, never inside a scientific directory and never a cache under the user home. Locked by `tests/test_workflow/test_cache_contract.py`.
- **Atomic persistence** — all JSON writes use temp-file + `os.rename`; workflow-layer writes go through `workspace.atomic_write_json`.
- **Values-on-edges lowering** — the workflow DAG is lowered to a frozen molab-owned `ExecutionPlan` (`workflow/_engine/plan.py`) executed by the structural engine (`engine.py` `run_plan`): each task's inputs are delivered from its upstreams' outputs (declared `depends_on` wins; trigger-carried values reach dep-less targets — the loop-back/branch-routed input channel), a task launches exactly when its dependencies are satisfied, and deadlock is detected structurally (`WorkflowDeadlockError`, zero timing constants). The engine is fully self-owned: the pydantic-graph dependency was removed, `End` is molab's own sentinel (`workflow/types.py`), and no `src/` module may import `pydantic_graph` (full-src AST scan in `tests/test_workflow/test_engine_boundary.py`). A parallel-join and a loop-`until` cannot be fused onto the same task — use separate tasks.

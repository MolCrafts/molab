# CLAUDE.md

molab is an agent-assisted scientific-workflow platform for FAIR research — Python (FastAPI + PydanticAI + a self-owned workflow engine) + TypeScript/React 19 UI, shipped as one wheel.

## Where things live

- Python source: `src/molab/` · TS source: `apps/web/src/` (VS Code ext: `apps/vsc-ext/`)
- Tests mirror source: `tests/` ↔ `src/molab/`, `apps/web/src/` for the web UI
- Public docs: `docs/` · in-flight specs: `.claude/specs/` (gitignored)
- **Detailed module map: `.claude/notes/architecture.md`** — keep that file as the index; CLAUDE.md only carries invariants

## Hard invariants (do not change casually)

- **Plugin host; atom is one model call.** molab is plugins composing each other. The host is `molab.harness.host` (DeepSeek/Cordis discipline: `ctx.xxx` attribute access, inject/apply/effect, no `ctx.agentLoop`). The atom is one pydantic-ai call via `ctx.llm` (one-shot `complete_*`, or one ReAct `stream_agentic`). `ChatLoop` / `InteractiveLoop` are deleted. Chat is one primitive call and must not loop. Tool-using work is one ReAct (stop when the model stops calling tools). **Plan is a `molab.workflow` graph**: each node is one call/ReAct whose products persist as artifacts. Workspace/workflow publish `ctx.workspace` / `ctx.workflow` and may register on `ctx.tools`; the model sees only `ctx.tools`. Full discipline: `.claude/notes/harness-plugins.md`.
- **MolRec layering:** molrec is a **protocol**, not a library — follow it by convention; **never `import molrec` in production** (a conformance suite, if added, is a test-only extra). A molab **Run is a host**, not a MolRec record (`run.json` + run-root `alive` ≠ molrec `meta` / `status`). Scientific packages follow the external spec (Zarr root). **Nobody owns a format except the package that can parse it.** molrs owns the solver formats; molplot displays and **registers no reader**, molab ships none either. **The frontend never asks Python about a format.** The server is a filesystem to it: list an attempt's files, hand back bytes. Everything else — which file is plottable, what the numbers mean — is decided in the browser by a `MetricReaderContribution` (`format` / `patterns` / `claims(text)` / `read(source, request)`) contributed by `plugins/molrs`, which parses via **molrs-wasm**. A chart therefore comes straight from `log.lammps` with no server-side parsing, and adding a format needs no server change. There is no `/molplot` read route and no format endpoint; `molplot/ingest` (persist to the WAL) is the only server-side format path that remains. `@molcrafts/molrs` is imported **only** through `lib/molrs.ts` (one WASM instance; no plugin depends on another) and every export is feature-detected, so a binding that predates an export disables that format instead of crashing. Nothing is privileged — molab's own `*.mlp.jsonl` is contributed like any other format. **The viewer sets the resolution, in simulation steps**: molplot passes `MetricReadRequest.stepInterval` ("a point every 10 000 steps") and each reader thins **per series** on the step axis. Never per row — a solver's thermo frequency changes between restart blocks (a real run here writes every 576-1000 steps), so every Nth row samples one stretch of a run denser than another, and the viewer would have to know a row count it cannot know. A record with no step is a one-off scalar and is always kept. Readers cache parsed tables by `path@revision` so a re-read re-slices instead of re-parsing. Server-side, the same formats reach `ingest_run` through the `molcrafts.metric_readers` entry-point group (molpy → molrs-python) — one Rust parser, two bindings, never two implementations. `molab.plugins.metrics` still owns the *writing* surface (`out/<stem>.mlp.jsonl` WAL) through the `workspace.metrics_seam` inversion seam; ingest persists reader output there and is always **optional**, and must exclude its own destination or it reads the file it is appending to. Conventions live in molab / molvis / molplot products, not UI-plugin patches. **Charts: molplot only** — molvis opens structures (PDB / XYZ / dumps / `*.mrec` Zarr) and claims no solver log, so no file is offered behind two tabs one of which cannot draw it. There is no server-side log parser either: the `lammps-log` route and its `LammpsLogResponse` schema are gone, because a regex in a FastAPI handler is a second implementation of a format molrs already owns.
- **The harness is a consumer of molab, not a layer inside it.** `molab.harness/` is a self-contained subtree — host + stages + `agent/` + `services/` + `server/` + `cli/` + `mcp_capabilities.py` — that sits **above** everything else and depends on it. **molab core contains zero imports of `molab.harness`** (AST-enforced by `tests/test_import_direction.py`, function bodies and `TYPE_CHECKING` blocks included). It ships in this wheel today, but it reattaches only through public seams, so extracting it later is a file move plus a dependency, not an architecture change:
  - **CLI** — `molab.cli_plugins` entry point → `molab.harness.cli:CLI_PLUGIN`. `molab plan` / `agent` / `curate` / `harness` exist exactly when the harness is installed. A plugin attaches to the app it is handed and **never reaches into another package's command tree** (this is why host introspection is `molab harness dump-config`, not a subcommand grafted onto molab's `config` group).
  - **Server** — `molab.server_plugins` entry point → `molab.harness.server:SERVER_PLUGIN` (`register` / `startup` / `signal_shutdown` / `shutdown`). Same process, same port, same session cookie; `create_app` never names a route module it does not own. **A plugin owns its wire**: the harness's request/response models live in `molab/harness/server/schemas.py`, not in molab's `server/schemas/`.
  - **UI** — `molab.ui_plugins` entry point (bundle served from `/api/plugins/{id}`).
  - **Inversion seams** — `molab.workflow.set_workflow_recoverer` (the generated-`workflow_source` shape), `molab.workspace.metrics_seam`, `molab.workspace.run.set_run_executor`.
- **Layer DAG** below the harness (enforced by `tests/test_<layer>/test_import_guard.py`): `services → workflow + workspace`, `workflow → workspace`. `molab.services` (`operator_config` / `run_failure` / `auth`) sits below CLI/server — CLI and server import services, never each other, and **services must not import the harness**. Any other arrow is an architectural defect.
- **Workflow public API**: decorator and OOP styles on `Workflow`; `WorkflowCompiler().compile(workflow)` produces the frozen `CompiledWorkflow`. Never mix them: `Workflow` is the authored graph (no `.compile()`), `WorkflowCompiler` is not a builder (`WorkflowCompiler(name=…)` is gone). Task bodies may be plain `def` **or** `async def` (sync bodies run via `asyncio.to_thread`, never blocking same-level parallelism). `Workflow` / `WorkflowCompiler` / `TaskContext` / `WorkflowRuntime` / `execute_run` / `aexecute_run` are re-exported lazily at the top level (`molab.WorkflowCompiler`, …) — `import molab` must stay light (no `pydantic_graph` in `sys.modules`; the dependency itself was removed).
- **Interface naming contracts (frozen — reject new spellings).** `params` is the one kwarg spelling across the hierarchy (`add_experiment(params=…)` / `add_run(params=…)` / `run(wf, params=…)`). `cancel` is the stop verb (see verb law); the operator config key is `agent.model` (`~/.molab/config.json`, bridged into `molab.config` by `services/operator_config.py` — CLI and server share one loader). Knowledge documents use `write` / `read` (not `set_body` / `body` / `write_head`). Run working paths: `run.path` (alias `run.run_dir`) is the run root as `pathlib.Path`; `workdir` is the current context's scratch (`RunContext.workdir` / `TaskContext.workdir`) — never `work_dir`. The disk is `workspace.fs` (`FileSystem`: local / remote / cached) — Folders do not own a filesystem. User byte writes go through `folder.files` (`FileStore` rooted at that folder). Run identity (`run.json`) holds only the logical definition (params / `definition_hash` / revision links); hot state and results live in the per-attempt `executions/eNN/execution.json` (`Execution`), and the owner heartbeat is the mtime of the per-Execution `alive` file (missing is not stale). Disk writes under a run go through one `FileStore` (`ctx.files.put` / `append`, atomic via `molab.atomicio`): products under `executions/eNN/out/`, `run.json`, `executions/eNN/workflow.json` / `execution.json`. Catalog rows are orthogonal (`ctx.register(path, kind=…)`); `register_artifact` is the compose of put-into-`executions/eNN/out/` + register. Cache stores return JSON + content-addressed blobs under `.molab/cache/`, never writes `out/` itself. Query the catalog with `{scope}.assets`; import external data with `{scope}.data_assets.import_asset`. Do not add `ctx.artifact.save`, `ctx.folder`, `register_asset`, or `reregister_artifact`.
- **`Workspace → Project → Experiment → Run` is a `Folder` family.** Generic CRUD (`add_folder / get_folder / has_folder / list_folders / remove_folder`) + typed semantic sugar per subclass (`add_project / add_experiment / add_run / …`). **There are no children-index files** — the directory tree *is* the index, so `list_folders` scans the container and nothing can drift from disk. `get_folder` / `has_folder` / `remove_folder` accept a directory name, a display name, or the entity's id. `add_project` / `add_experiment` are idempotent on display name; `add_run` is idempotent only on an explicit `id=` — every other call allocates a fresh run.
- **Agent public surface**: `AgentRunner`, `AgentRunResult`, `AgentRuntime`, `AgentSession`. New work calls pydantic-ai through `Router` / `AgentGateway.call` only. Do not grow `ChatLoop` or `InteractiveLoop`. ("Loop" is not a molab product concept; ReAct is pydantic-ai's. Plan orchestration is a workflow, not a Mode.)
- **OpenAPI surface** under `src/molab/server/routes/`; the web UI regenerates against it (repo root: `npm run generate:api`). Don't hand-edit `apps/web/src/api/generated/`.
- **Private subpackages** — never import from outside their owning layer: `workflow/_engine/` (the self-owned execution engine), `harness/agent/_pydanticai/`, `harness/agent/mcp/`.
- **The self-owned engine and molq are evaluated decisions, not defaults.** Temporal / Ray / AiiDA / PSI/J were each assessed against source and release data and rejected as replacements (they lose on the one-source-of-truth law and on one-wheel distribution). Standing verdicts, the adopted borrow-list, and the evidence live in `.claude/notes/upstream-comparables.md` — re-propose a replacement only by arguing against that file.

## Architecture

```
  molab.harness/          the agent product: plugin host (atom = AgentCall),
    │                      plan/chat/curate bundles, agent/ (Router, ReAct,
    │                      sessions), services/, server/, cli/
    │  attaches via entry points + inversion seams — never imported by name
    ↓
  molab                   the scientific-workflow platform
    ├─ cli, server         application shells
    ├─ services            operator_config / run_failure / auth
    ├─ workflow ─→ workspace
    └─ knowledge, workspace
```

Inside the harness subtree the composition is unchanged: the host injects `agent` (Router / one-shot or ReAct; no molab-owned loop kernel), `workflow` (compile / execute / resume plugin) and `workspace` (Folder / Run / assets plugin) as `ctx.xxx` services.

molab's own Server + CLI sit on top of **`molab.services`** (the application-service layer: `operator_config` / `run_failure` / `auth` — one backend code path for "Python 操作 = UI 操作"); the harness's equivalents live in `molab.harness.services` (`plan_runtime` / `curate_runtime` / `agent_task_store` / `agent_context` / `approval_notify` / `agent_task_llm_cache`). UI is downstream of the server's OpenAPI. Cross-layer primitives (`molab.path`, `molab.profile`, `molab.entry`, `molab.atomicio`, `molab.ids`, …) sit above workspace and may be cited from any layer. **`molab.knowledge`** is a **bottom** layer that owns only the Open Knowledge Format concept-type registry (`@concept_type` / `register_concept_type` / `resolve_concept_type`); the OKF-native storage substrate lives in `molab.workspace`, which uses this registry to reconstruct typed `Folder` subclasses from each Concept's persisted `type`. `knowledge` is a peer of `workspace` and imports neither it nor any upstream layer. `molab.config` is the process-global in-code config — a live `molcfg.Config` instance defined in `molab/__init__.py` (LLM keys etc., registered in code, never from env); `molab.profile` is the separate file-based, per-run profile config (`ProfileConfig` / `MolCfg` / `load_molcfg`).

### Layer charters

**`molab.fs`** — layer-0 primitive; the filesystem seam, shared by `workspace` and `knowledge`.
- Owns the `FileSystem` Protocol + `PathArg` / `StatResult` / `DirEntry` (`base.py`), the single `LocalFileSystem` (`local.py`), and `memo.py` (`StatMemo`) / `profile.py` (`FsProfile` / `detect_fs_profile`) / `window.py` (`read_text_window`). `fs_remote` / `fs_cached` stay in `workspace` — they bind `molq`, and keeping them there is what makes `import molab.fs` stdlib-only (locked by `tests/test_fs/test_import_weight.py`); every module added here stays stdlib-only too.
- **One** `LocalFileSystem` class, re-exported by `workspace/{fs,fs_local,gitignore}.py` as the *same object*. This is load-bearing: `Folder.move_to` gates on `isinstance(self._fs, LocalFileSystem)`, so a second parallel class would make that check silently False on a perfectly local tree.
- **`scandir` and `read_range` are required Protocol members**, not optional accelerators: `scandir(path, *, with_stat=True)` answers name+type+size+mtime in one syscall / round-trip, and `read_range(path, offset, length)` reads a window. Every implementer (Local, Remote, Cached, and every test fake) implements both. A walker reaching for `listdir` + per-entry `is_dir`, or a reader slurping a whole file to show its tail, is the bug pattern this exists to prevent.

**`molab.knowledge`** — bottom layer; path-identity knowledge, usable with no workspace, plus the open concept-type registry it is built on.
- **A Knowledge document is a directory.** Path is identity: `Note(path)` holds an absolute path and a `FileSystem`, has no parent pointer, and composes no path from a hierarchy. The head is **class-named json** (`note.json` / `literature.json` / `report.json` / `finding.json` / `plan.json` / `observation.json`) plus `index.md` (narrative whose markdown links **are** the graph). There is no knowledge `meta.json` and no `type`/`kind` key on the head. Reconstruction is `Knowledge.open(path)` from the filename. User verbs: `write` / `read` / `cite` / `links` / `search(..., of=Note)` / `walk`.
- **Six subclasses of `Knowledge`:** `Note`, `Literature`, `Report`, `Finding`, `Plan`, `Observation`. Failure analysis is a `Report`; harvest of a scientific outcome is a `Finding`. Harvest targets are the subset Finding / Observation / Report.
- Owns: `types.py` (the registry), `concept.py` (`Knowledge` handle / `open` / `walk` / `search` / `cite`), `concepts.py` (the six classes), `knowledge_item.py` (`SourceRef`), `edges.py`, `bundle_index.py` (internal), **`retrieval.py`** (CJK-aware `tokenize` + `bm25f_rank`, stdlib only), **`sources.py`** (the named-wiki registry), `zotero.py`, `hooks.py`, the `*_meta.py` heads. `Bundle` / `Backlink` / `BundleIndex` are walk internals, not `molab.knowledge.__all__`.
- **Knowledge is not a Folder.** Workspace `Folder` subclasses compose a path from a parent chain; `Knowledge` *is* its path. Workspace mounts documents under `knowledges/<slug>/` via `write_knowledge`. Agent session `meta.json` and the harness Plan plugin (`task_board.json`) are not knowledge product classes.
- **Retrieval is keyword ranking, not RAG.** BM25F over title/tags/path/body; CJK runs emit unigrams **and** adjacent bigrams so IDF self-balances — no segmenter, no dictionary, no embeddings.
- **A read never writes.** `search()` and the scans build the index in memory and return it.
- **Allowed imports**: stdlib, pydantic, pathspec and the layer-0 primitives `molab.fs` / `molab.gitignore` / `molab.ids` / `molab.path` / `molab.atomicio` / `molab._typing`. **MUST NOT** import `workspace` (a *peer*) or any upstream layer (`workflow` / `agent` / `harness` / `services` / `server` / `cli` / `plugins`) — enforced by `tests/test_knowledge/test_import_guard.py`, an **AST source scan** (not a `sys.modules` probe: `molab/__init__.py` eagerly loads `workspace`, so a runtime probe is unsatisfiable).

**`molab.workspace`** — bottom; pure storage.
- Owns: `Folder` base + the `Workspace/Project/Experiment/Run` subclasses, typed exceptions (`*NotFoundError` / `*ExistsError`), atomic JSON I/O (`atomic_write_json`), the `Asset` family + per-scope `AssetManifest` (`assets.json`) + the `assets.scan` manifest-scanning query layer (`scan_assets` / `get_asset` / `find_by_content_hash`), `Params` / `ParamSpace` / `GridSpace` / `UniformSpace`, the **unified Target family** (`ComputeTarget` is the persisted base; `LocalTarget` / `RemoteTarget` are its address-view subclasses; `resolve_compute_target` is the single named-target resolution path for CLI and server; `SSHSession` for transport caching), `RunContext`, `RunSet` / `RunSetResult` (sweep container: `experiment.sweep(...)` → `runset.execute()` → `to_records()` / `min_by()`; execution delegates through the `set_run_executor` inversion seam so workspace never imports workflow), zombie reaping (`run_reaper.reap_zombie_run`, called by every CLI **and** server verb entry), run-lifecycle verb cores (`lifecycle_ops.cancel_run`; two-phase `prune.plan_execution_prune` / `apply_execution_prune`), execution→knowledge (`harvest.harvest_run`), the knowledge mount (`write_knowledge` under `knowledges/<slug>/`, `Note` / `Literature` / `Report` / `Finding` / `Plan` / `Observation` from `molab.knowledge`, `ZoteroItem` / `read_zotero_items` — surfaced as `molab knowledge import-zotero`), and one optional folder accessed as a lowercase property: `ws.cache` (`CacheFolder` → `as_cache_store()` adapter; execution auto-cache does **not** use this — it writes `run_dir/cache`). **There is no derived asset index** — asset queries scan the authoritative per-scope `assets.json` manifests (+ directly-registered `assets/<slug>/asset.json` records), and emitted products are read from the Executions that own them (`artifact_repository.scan_artifacts`).
- **Notes + literature are `molab.knowledge` documents** (`Note` / `Literature` plus `Report` / `Finding` / `Plan` / `Observation`) — directories whose path is their identity (bib fields in `literature.json` via `ReferenceMeta`; PDFs *pointed at*, never copied). `workspace` **mounts** them into its tree through **`write_knowledge`** / **`knowledge_mount`** (`mount_note` / `embed` / `entity_summary`) and re-exports the names; it does not define them. `Folder` and `Knowledge` stay **independent base classes** — a `Folder` composes its path from a parent chain, a `Knowledge` *is* its path. The legacy per-scope `Library` (record-`Reference` / `ReferenceStore` / `NoteAsset` / `LibraryIndex` / `.library` properties / `search_library` agent tool / `/api/library` routes / UI Library page) was removed in wsokf-11; greenfield, no migration.
- MUST NOT: import any upstream `molab` layer (`workflow` / `agent` / `plugins` / `services` / `server` / `cli`). Allowed `molab.*` imports are only `_typing` / `profile` / `path` and cross-layer primitives (`mollog`, `molcfg`). MUST NOT define workflow- or agent-shaped types (no `WorkflowSnapshotRef`, no `Agent` / `AgentSession` / `PlanFolder`). The OKF `Plan` Concept (`knowledge.plan`, `plans/<id>/`) is knowledge storage, not the harness Plan plugin. MUST NOT write to disk in `__init__` — all I/O is lazy.
- `import molab.workspace` must never pull `molab.workflow`, `molab.harness`, `pydantic_ai`, or `pydantic_graph` into `sys.modules`.

*Identity & persistence law (workspace).*
- **A Run's `definition_hash` has one implementation and does not name a path.** `molab.workspace.run.compute_run_definition_hash(experiment_revision_id, parameters, input_asset_ids)` is the only place a run's definition is hashed — `Experiment.add_run`, `_seed_missing_runs` and `Run.__init__` all call it (they used to hand-roll two different digest shapes, and the server folded a synthesized `workflow_snapshot` in while `Experiment.define` did not, so the same experiment + params got a different identity depending on which door created it). **The workflow is the experiment's property, not the run's**: `ExperimentMetadata.workflow_entrypoint` (the `"<file>:<qualname>"` locator) is written once by the single binding seam `molab.entry._execute_experiment`, which every `define` / `sweep` / `run(wf)` reaches, and `molab.workflow.recovery` resolves it through the run's parent. Nothing writes a per-run copy any more — `RunMetadata.workflow_snapshot` is a read-only legacy field. Locked by `tests/test_workspace/test_run_identity.py`.
- **Three orthogonal id layers, no fourth.** Uniqueness → `generate_uuid7()` (time-ordered UUIDv7 for Project / Experiment / Run / Artifact; an Execution is identified run-locally as `e01` / `e02`, so `(run_id, execution_id)` is the global handle). Reproducibility & dedup → content hashes: `definition_hash` (`"sha256:…"`) is a run/experiment-revision's *one* reproducibility identity, `compute_content_hash()` addresses artifacts. Location → `AssetScope(kind+ids)` + `execution_id`. A run carries exactly one identity — never add a second parallel run-fingerprint type alongside `definition_hash`.
- **Identity is never the path.** A directory name is a *name*, for people: `experiments/<slug(name)>`, `runs/<key=value_…>` (its parameters, sorted; a digest when there are none), `executions/e01`. The UUIDv7 lives in the entity JSON's `id`, which is what cross-entity references cite — so renaming a directory breaks nothing, and `ls` tells you what was run. `molab.workspace.naming` owns every derivation. **A client therefore never composes a workspace path.** Every entity response carries `path` (`ProjectResponse` / `ExperimentResponse` / `RunResponse` / `WorkspaceRunRow`, via `schemas.responses.workspace_relative`), and `RunResponse.name` is the run's parameters; the UI reads both and derives neither, because an id-composed path names a directory that was never created.
- **Run vs Execution.** `Run` = immutable logical intent (params + workflow + revision/definition links, persisted as `run.json` = definition only); `Execution` = one physical attempt, `e01` / `e02` / …, N-per-run. **One attempt is one file**: `executions/eNN/execution.json` (`Execution`: mode, status, ownership, started/finished, executor, environment, emitted artifacts, evidence, error, seal) is the whole of it — there is no second sealed record elsewhere, no `artifacts/<id>/artifact.json`, no `environment.json` / `exception.json` sidecars. Sealing sets `sealed_at` and freezes the terminal fields in place. Cross-attempt reproducibility identity stays at run level (`definition_hash`). An Execution persists completed-task outputs at **workflow-node granularity**, so a failed attempt can be resumed in place (next bullet).
- **Execution modes (five, all on the same `run_id`; there is NO new-Run operation).** `ExecutionMode` is `INITIAL` (first attempt, no predecessor) / `RETRY` (requires a failed/cancelled/interrupted predecessor) / `RESUME` (requires a checkpoint artifact from the predecessor) / `RERUN` (fresh attempt from the top) / `REPRODUCE` (requires a succeeded predecessor). Cloning params into a fresh `run_id` is NOT a molab operation. **Success requires evidence**: an attempt that runs nothing flips nothing — the sealed `Execution`'s terminal status is the engine's signal (`succeeded` / `failed` / `cancelled` / `interrupted`); a task failure is recorded on the `Execution` itself and its traceback lands in that attempt's `run.log`.
- **Run status is derived, not scalar.** A `Run` has no scalar `status`; callers read `run.status_summary` (a `RunStatusSummary`: total/active/not_started/by_status) or `run.executions` (ordered `Execution`s). `Run.is_retryable` is true when any Execution is terminal `failed`/`cancelled`/`interrupted`. `cancel` targets one active Execution id (`run.cancel(execution_id)`) — a Run itself is not scalar-cancellable. A stale `running` Execution is reaped to `failed` *before* any verb decides — same-host with a dead owner PID, or **cross-host only when the per-Execution `alive` exists and its mtime is older than 600 s** (touched every 30 s by the owner; missing `alive` is not stale — a live HPC job that has not claimed yet). CLI / server / the Python one-step API (`molab.execute_run(wf, run, …)` / `Run.execute` / `RunSet.execute`) share the same Execution-mode path via `ExecutionRepository`; the CLI noun group stays plural (`molab runs …`) deliberately (typer's flat per-level namespace means a `run` group would shadow the top-level `molab run` verb).
- **One source of truth — and it is the files.** Entity `*.json` + per-scope `assets.json` asset manifests are authoritative, full stop. There is **no** second store to reconcile: no `index/`, no `provenance/` event tree, no content-addressed `content/`, no children-index `*.json`. A query is a walk of the tree (`list_folders`, `assets.scan`, `artifact_repository.scan_artifacts`). Never add a file whose only content is a copy of something already on disk.
- **History is git.** The workspace is a git repository; every mutation ends in a commit whose message trailers carry the typed fact (`Molab-Event` / `-Subject` / `-Agent` / `-Rel` / `-At`), so `git log` is the provenance query and `git push` is the backup. `molab.workspace.GitHistory` owns it, `molab history {log,init,sync,push}` is the CLI. History is a **soft** dependency: nothing reads it to answer an operational question, and a worker that cannot take the commit lock leaves its files for the next commit — science never blocks on git.
- **An attempt's directories are peers, and their meaning is data.** `molab.workspace.execution_dirs` declares each one (`ExecutionDir`: `name` / `purpose` / `versioned` / `products`) and **every** question about them is a query, never a string match: the workspace `.gitignore` is generated from `versioned`, the metrics WAL searches `products`, the layout validator's legal-name set is `execution_dir_names()`. Three tiers — `work/` (framework scratch: plan boards, harness staging, landing), `out/` (**where a workflow task writes**: `ctx.task_workdir(t)` / `TaskContext.workdir` is `out/<task>/`; bulk, kept on disk, gitignored), `artifacts/` (promoted, registered, versioned) — plus `jobs/` and `checkpoints/`. A task body's output is genuinely mixed (its generated inputs, its intermediates, its trajectory) and cannot be sorted from outside, so it lands in the tier that is *kept*, never the disposable one; `register_artifact` / `emit_artifact` then promotes anything citable into `artifacts/` from **any** tier. Bulk stays out of git by file-type patterns regardless of tier, so a trajectory promoted into `artifacts/` is still not committed. One accessor reaches all of them — `ctx.get_dir(name, *parts)` / `has_dir` / `list_dirs`; there is **no** per-directory property (`ctx.workdir` is gone, and `PRODUCTS_DIR` with it), and an undeclared name raises `UnknownExecutionDirError` rather than creating a directory nothing validates. Registration is open, so a package declares the directory it writes. The server ships the declarations on `RunFilesResponse.dirs`, which is how the UI knows a `.mlp.jsonl` under `products` is a result and the same name under scratch is not — **the frontend never infers a directory's meaning from its name**. `TaskContext.workdir` keeps its name (frozen; the engine canonicalises it out of the cache key and it may be `None` off-workspace) — it is the *role* name for where a task works, and the directory it resolves to is `out/<task>/`.
- **Machine state lives in `.molab/`.** Locks, the workflow node cache, anything a person never opens. A scientific directory contains science. `.molab/` is gitignored and can be deleted whole.
- **No speculative code in `src/`.** A subsystem with zero production callers does not ship. "Future" capability with no live call-path belongs in docs or a branch, not the tree.

**`molab.workflow`** — middle; graph execution engine.
- Owns: `Workflow` (decorator + OOP, mutable) → `WorkflowCompiler().compile(workflow)` → `CompiledWorkflow` (frozen, content-hashed). `Task` / `Actor` convenience bases; user-facing protocols are `Runnable` / `Streamable`; task bodies may be sync or async. `TaskContext` (the single context for batch + streaming bodies), `TaskTypeRegistry`, `TaskSnapshot` (AST-normalized hash), `Caching` (LRU), `WorkflowSnapshotRef`, `WorkflowResult` / `WorkflowExecution` (result-level status vocabulary is `succeeded`/`failed`; legacy persisted `"completed"` is normalized on read), `End` (molab-owned sentinel in `workflow/types.py` — generic frozen dataclass, `End()` / `End(data)`; defined exactly once), `Next` (routing return value for `wf.branch` / `wf.loop`), `promote_callable()`, and `execute_run` / `aexecute_run` (one-step tracked execution + the `RunFailedError` / `RunNotExecutableError` pair; registers the workspace `set_run_executor` seam at import so `Run.execute` / `RunSet.execute` reuse the exact CLI execution path). Private `_engine/` is the self-owned execution engine — **pydantic_graph is no longer a dependency and must not be imported anywhere in `src/`** (enforced by `tests/test_workflow/test_engine_boundary.py`, a full-src AST scan).
- Uses workspace: `Workflow.execute(run=…)` takes a `workspace.Run`; `Caching` is backed by `run_dir/cache` (auto from `RunContext`) or an explicit `CacheStore`; run-state JSON writes go through `workspace.atomic_write_json`.
- **resume is task-granular, caller-driven, and self-validating.** A failed run preserves completed outputs in `WorkflowResult.outputs`; the caller (CLI/server) re-seeds them via `runtime.execute(..., seed_outputs=…)`, sourced from the *existing* execution's persisted node-level state. Node state is persisted **incrementally** to `executions/eNN/workflow.json` (per-task status + outputs + `snapshot_key` + `outputs_lossy` flag — not per-frame engine checkpoints; within-task checkpointing belongs to `ctx.workdir`). At seed time the engine drops (warn, recompute — never error) any seed whose recomputed `TaskSnapshot.key` differs (code changed), whose outputs were lossy-truncated, or which cannot be verified (pre-flag documents). Seeded nodes are recorded in `WorkflowState.seeded` and skip their body (`from_seed`); unknown seed names fail-fast. `rerun` simply calls `execute` with no seed (new `exec_id`). SubWorkflow inner runs execute with persistence off — `executions/eNN/workflow.json` always describes the **outer** graph only.
- MUST NOT: import `agent` / `plugins` / `server` / `cli` / `services`. MUST NOT import `pydantic_graph` anywhere (the dependency is removed). No second `End` sentinel (single definition in `types.py`), no per-task node-class codegen. `Next` is public (the `wf.branch` / `wf.loop` routing return value, in `molab.workflow.__all__`) but stays out of the frozen top-level `molab.__all__` / lazy re-exports.

**`molab.harness.agent`** — inside the harness subtree; pydantic-ai facade + LLM-only loops.
- Owns: the public surface (`AgentRunner`, `AgentRunResult`, `AgentRuntime`, `AgentSession`). `AgentRuntime` is the frozen-dataclass bundle (`session` + `router` + `execution_env`). Flat module list — `loop.py` (`AgentRunResult`) / `react.py` (one ReAct turn) / `runtime.py` / `session.py` / `session_storage.py` / `session_entry.py` / `events.py` / `compaction.py` / `execution_env.py` / `router.py` (Protocol) / `runner.py` / `folders.py`. `loops/` is hook vocabulary only. Private `_pydanticai/` is the **sole** sanctioned `import pydantic_ai` site.
- Uses workspace only (`Folder`, `Workspace`, `Run`, `RunContext`, …) for on-disk session storage. Pipeline orchestration lives in the harness proper and reaches the agent through the `AgentGateway` Protocol — the agent never calls back up into it.
- MUST NOT: import the rest of the harness, `molab.workflow`, `molab.plugins`, `molab.services`, `molab.server`, `molab.cli`. MUST NOT import `pydantic_ai` outside `_pydanticai/`. MUST NOT import `pydantic_graph` anywhere.
- Don't reinvent what pydantic-ai already does. Plain tools → `Agent(tools=[…])`; MCP servers → `Agent(toolsets=[MCPServerStdio(…)])`; retries → `Agent(retries=N)`; message history + structured output → pydantic-ai native. The agent layer (Session persistence, AgentEvent stream, on-disk folders) is what molab owns; if pydantic-ai *cannot* do something, say so in the new module's docstring.
- `import molab.harness.agent` must not pull `pydantic_ai` or `pydantic_graph` into `sys.modules` until `AgentRunner.run()` is actually called.

**`molab.harness`** — the agent product, above all of molab; plugin host (AgentCall + lifecycle) and the default orchestration / policy / store plugins. Owns its own `agent/`, `services/`, `server/` and `cli/` subpackages. `Plan` is the `plan` bundle, not the kernel. See `.claude/notes/harness-plugins.md`.
- Owns: artifact lineage + audit + execution machinery (`HarnessRunContext`, `Stage`, `StageRunner`, `ArtifactStore` + `FileArtifactStore`, `EventLog` + `JsonlEventLog`, `ArtifactLineageStore` + `FileLineageStore`, **`ApprovalStore` + `FileApprovalStore`**, `CapabilityRegistry`, executors, validators, `ApprovalGate`, `generate_audit_report` + replay, **`workflow_recovery`**, curation + lifecycle capability catalogs). Run-level provenance (params, config hash, code/script identity) is owned by **workspace** (`RunMetadata` + per-scope `AssetManifest`); harness lineage covers agent-pipeline artifacts only and stamps each edge with stage + workspace `run_id`. The plan pipeline is **two-phase planning→realization**, composed by `Plan` (`harness/modes/plan.py`); stages live under `harness/stages/`. **Phase 1 — plan workflow**: `Plan` runs a `Workflow` graph (`assemble_knowledge → draft_board ⟲ form_check → probe → persist → render → review → freeze → realize`). Each LLM node is one `AgentGateway.call`. Form failure is `wf.loop`, not an agent outer loop. Board tools register on `ctx.tools` (unload drops them). A malformed board never reaches the review gate. `PlanReachabilityProbe` read-only-annotates each board task's feasibility (molmcp grounding, no binding), a deterministic form guard re-checks, the current `ExperimentPlan` (spec + board) is persisted as the `experiment_plan` review subject, and a **hard** `StepAuditLoop` review gate runs store-first (suspends with `ApprovalPendingError` + a durable pending record; a stored grant replays). On grant, `freeze_experiment_plan` writes the content-addressed `frozen_experiment_plan` and the `plan_report_renderer` agent emits the report. **Phase 2 — deterministic realization** (`RealizeBoard`, `harness/stages/realize_board.py`): a map→reduce→compile realizer over the frozen board — one codegen self-repair worker (`realize_one_task`, sharing `harness.stages.task_codegen`) per task **in parallel** (full coverage by construction), reduce the greens into a single `workflow_source`/`test_source`, then `MaterializeExecution → CompileWorkflow` (`run_workflow.py --compile-only`, **no** real science; `execution_result` tagged `metadata.mode="compile"`). A task that never greens by the attempt ceiling returns *blocked*; any block persists a durable `intervention_request` then raises `TaskRealizationBlockedError` **before** compile — never auto-reverting to phase 1. The `harness/gateways/` subpackage holds the `AgentGateway` Protocol + `StubAgentGateway` (test stub) + `RouterBackedAgentGateway` (production impl whose `call` dispatches on `AgentCallSpec.call_mode` — degenerate `complete_structured` vs full `stream_agentic` ReAct — driven by `agent.router.Router`); the plan LLM-agent registry (schema + output-kind + system-prompt per `agent_name`) is the single shared `harness.gateways.plan_agents`. Both phases persist raw-before-parsed artifacts with consistent lineage; the plan graph itself runs in-process via `WorkflowRuntime` (persisted on the plan Run); science compile still loads the engine only in executor subprocesses (`LocalExecutor` / `DryRunExecutor`). Cross-process suspend/resume is **scope-tagged and durable** (`ApprovalScope` `approval_gate` vs `intervention_request` on the run's `FileApprovalStore`; the shared `services.plan_runtime` resume path rebuilds the scoped session and replays). **Production entry point: `molab plan` (`cli/plan_cmd.py`) and `POST /plan-tasks`** both drive `Plan.execute` against a content-addressed Run; artifacts land under `run_dir/artifacts`, events in `events.jsonl`, approvals in `approvals.json`.
- Uses: its own `agent/` (LLM dispatch via `RouterBackedAgentGateway`), and molab's `workflow` / `workspace` / `services` / `server` / `cli`. **MUST NOT be imported by any of them** — enforced by `tests/test_import_direction.py`.
- `pydantic_ai` / `pydantic_graph` must not be transitively loaded when `import molab.harness` runs (they load lazily through `agent.AgentRunner.run()` only; pydantic_graph survives merely as a transitive install of pydantic-ai, never imported by molab).
- **Public surface is deliberately small**: `molab.harness.__all__` = **22 symbols** (locked by `tests/test_harness/test_public_surface.py`): the mode/Stage machinery (`Plan` / `Chat` / `chat_loop_config` / `Stage` / `StageRunner` / `HarnessRunContext` / `ModeResult`), stores + executors + gate + gateway (`ArtifactStore` / `FileArtifactStore` / `Executor` / `LocalExecutor` / `DryRunExecutor` / `ApprovalGate` / `AgentGateway`), the doc-cited set (`RouterBackedAgentGateway` / `CapabilityRegistry` / `StageExecutionError` / `JsonlEventLog` / `FileLineageStore` / `replay_metadata`), and the **approval-inbox pair** (`ApprovalPendingError` / `FileApprovalStore` — vision-loop-01: gates suspend with a durable pending record in `approvals.json`, never a hard failure; grants replay, rejections do not). Stages / schemas / validators import from their subpackages (`harness.stages.*` / `harness.schemas.*`), never from the top level. Plan-owned schema names carry the `Plan` prefix to avoid cross-layer collisions: `PlanTaskIR` / `PlanWorkflowIR` / `PlanValidationReport` / `PlanArtifactRef`. `molab plan` and `POST /plan-tasks` both drive `Plan.execute`; the CLI shows a two-phase banner (interactive planning → deterministic realization). The plan CLI **preflights before any disk write** (model → agent-stack import → credential resolution, via `services.plan_runtime.preflight_plan_router`), so a failed `molab plan` leaves zero residue. Workflow reconstruction for plan-generated / script runs is **one path**: `harness.workflow_recovery.compiled_workflow_for_run` (CLI `molab run` and lifecycle capabilities share it). Built-in capability catalogs live under `harness.capabilities/` — `curation` (workspace reorg) and `lifecycle` (`run_execute` / `run_resume` / `run_rerun` / `run_cancel` / `runs_prune`, all side-effect-gated; execute is local-only in v1).

**`molab.services`** — application-service layer between CLI/server and the domain layers.
- Owns: `operator_config` (the one `agent.model` / `~/.molab/config.json` loader shared by CLI and server), `run_failure`, `auth` (filesystem users + sessions for `molab serve`). This is where "Python 操作 = UI 操作" is enforced: CLI commands and server routes both call services, never each other.
- The plan / curate / agent-task services moved into **`molab.harness.services`** with the harness: `plan_runtime` (background `PlanTask` + gateway preflight + `materialize` / `record`; scope-tagged durable suspend/resume; `ApprovalPendingError` is suspension, not failure), `curate_runtime`, `agent_task_store`, `agent_task_llm_cache`, `agent_context` (`build_mount_context` / `resolve_scope_dir` / `mount_session_scope`), `approval_notify` (in-process approval-change pub/sub feeding `GET /api/approvals/events`). The plan bundle itself is **`Plan.open` / `Plan.execute` / `Plan.save`**.
- Uses: workflow, workspace. MUST NOT: import `harness` / `server` / `cli` / `plugins` — enforced by `tests/test_services/test_import_guard.py` (AST scan); every lower layer's guard forbids importing `services` back. The harness's own services live in `molab.harness.services`.

## On-disk layout

This layout is the **authoritative experiment-directory spec** — the shape any tool restructuring data into a molab workspace must produce. Children indices are local conveniences rebuilt on `add_folder` / `remove_folder`. Per-attempt artifacts live under `executions/<exec_id>/`; cross-attempt state stays at the run level. Cross-cutting asset/lineage queries scan the authoritative per-scope `assets.json` manifests directly (`assets.scan`) — there is **no** derived SQLite asset index (the former `catalog/index.sqlite` was removed; see the One-source-of-truth law).

```
workspace_root/
├── .git/                         # the history: one commit per fact (molab history log)
├── .gitignore                    # bulk payload is reproduced, not versioned
├── .molab/                      # machine-only; deletable; never opened by a person
│   ├── locks/                    #   advisory locks (run, execution, history, assets)
│   └── cache/<run-path>/         #   workflow node cache, keyed by the run's path
├── workspace.json                # workspace ENTITY + OKF type (workspace.root)
├── index.md                      # OKF narrative; its markdown links ARE the knowledge graph
├── <agent>/                      # Agent (OKF concept, kind=agent.agent): meta.json + flat sessions
│   └── <session>/                #   AgentSession (kind=agent.session): meta.json + messages.jsonl
└── projects/<project-slug>/      # container "projects/", dir name = slug(project name)
    ├── project.json              # project ENTITY metadata (singular; holds the UUIDv7 `id`)
    ├── knowledges/<id>/          # Knowledge (class-named entity JSON, e.g. plan.json). NO meta.json
    └── experiments/<experiment-slug>/     # dir name = slug(experiment name)
        ├── experiment.json       # experiment ENTITY metadata (singular)
        ├── workflow.py           # the experiment's own script, beside the runs it produced
        ├── knowledges/<id>/      # Knowledge: Plan book is Plan/"plan-book" → plan.json + index.md
        └── runs/<dp=5_seed=42>/  # dir name = the run's parameters, sorted (digest when there are none)
            ├── run.json          # logical definition only (params / definition_hash / revision links)
            ├── approvals.jsonl   # harness RunApprovalStore (append-only, survives across attempts)
            ├── plan/             # harness Plan plugin state (task_board.json)
            ├── events.jsonl      # harness JsonlEventLog
            └── executions/e01/   # one attempt; `e01` IS its id
                ├── execution.json  # THE attempt: status/ownership/executor/environment/
                │                   #   artifacts/evidence/error/seal — nothing else, nowhere else
                ├── alive           # empty file; owner heartbeat is mtime (missing ≠ stale)
                ├── workflow.json   # per-node state, for resume
                ├── run.log         # the attempt's one log (runtime + traceback)
                ├── artifacts/      # promoted + registered: metrics.mlp.jsonl, tg_fit.png
                ├── out/<task>/     # what each task wrote: trajectories, restarts, logs
                ├── jobs/<job>.{sh,out,err}   # scheduler evidence, flat — no dir per job
                ├── checkpoints/    # ctx.checkpoint payloads
                └── work/           # framework scratch (plan, harness); disposable
```

**Layout naming law (frozen).** Each `Folder` level obeys three derivations, all driven off the class hierarchy `Workspace → Project → Experiment → Run`:
- **Container subdir** holding a level's children is the child kind pluralized: `projects/`, `experiments/`, `runs/`, `knowledges/` (Knowledge family at project and experiment).
- **Directory name** within that container is a *name a person reads*, derived in `molab.workspace.naming`: `entity_slug(name)` for Project/Experiment, `run_slug(params)` for a Run (`dp=5_seed=42`; a digest of `definition_hash` when there are no params), `execution_slug(seq)` for an attempt (`e01`). No prefixes. Collisions get a `-2` suffix. The UUIDv7 identity lives in the entity JSON's `id` and never appears in a path.
- **Entity metadata filename** at a level is the level's own class name snake_case + `.json` (**singular**: `workspace.json` / `project.json` / `experiment.json` / `run.json` / `plan.json` / `finding.json`). WPER still stamps `type` on those files; Knowledge reconstructs from the filename (no `type`, no `kind`, no `meta.json`). Notes / Agent sessions still use `meta.json`.
- **There is no children-index filename.** A parent's children are its entity subdirectories; `ls` is `list_folders`.

The entity `*.json` files are the whole truth. History is the workspace's git log (`molab.workspace.GitHistory`), which records each fact in commit-message trailers and is never read to answer an operational question. A Run is immutable scientific intent (`run.json` = logical definition only); everything about one attempt — status, ownership, executor, environment, emitted artifacts, evidence, error, seal — is in that attempt's single `executions/eNN/execution.json`, and the owner heartbeat is the mtime of the per-Execution `alive` file.

Restructuring an older workspace into this layout is `molab migrate layout <old> <new>` (`cli/migrate_cmd.py`): it renames every directory, folds each attempt's sidecars into one `execution.json`, drops what was only a copy, hard-links bulk payload, and commits the result. Renaming machine dirs after the molexp→molab cut is `molab migrate brand`.

Agent-layer mounts (`Agent` / `AgentSession`) are OKF `workspace.Folder` subclasses (registered via `@concept_type("agent.agent"/"agent.session")` against `molab.knowledge.types`); they can attach at any `Folder` (workspace root, Project, Experiment, or Run) through generic `add_folder`, and `concept_from_dir` reconstructs them from their `meta.json` `type` via the shared registry.

## Packaging

Python install and UI compile are **separate jobs**. Default `pip` / `uv pip` / `python -m build` **never** invoke npm.

- **Daily (checkout):** `molab serve --dev -ws ./lab` — open the printed **Dev UI** (`:5173`), not the API port. That starts `npm run dev:api` (real `/api` proxy). `npm run dev:web` is the MSW mock, not this path.
- **Bundled preview:** `npm run build:web` then `molab serve -ws ./lab` — open `:8000`. Editable installs read in-tree `src/molab/dist/`; **do not reinstall Python**.
- **Wheel:** `uv pip install . -C build-web=true` (never `-C build-ui=true` / `npm run build:ui`). Empty `dist/` → API-only.

```
apps/web/src/  →  npm run build:web  →  src/molab/dist/  →  setuptools  →  wheel
```

`src/molab/dist/` is gitignored (except `.gitkeep`); `create_app()` locates it via `importlib.resources.files("molab") / "dist"`. Command table: `.claude/notes/ui-serve.md`. Public: `docs/en/development/ui-serve.md`.

**UI component library:** prefer **shadcn/ui** when building UI features; if a shadcn component doesn't fit, document the reason in the PR description.

**UI server state:** **TanStack Query v5 is the only server-state cache** — `ui/src/app/state/queries/` owns the client, the `qk` key factory, and the invalidation map. A component does not fetch in a `useEffect` and does not keep server data in `useState`; a mutation calls a `useInvalidate()` helper for the keys it actually changed, never a global refresh. Polling is a fallback for when the SSE change stream is down, gated on data (a terminal run stops its own interval) and never runs on a hidden tab. `zustand` is installed but unused — do not reach for it for server state.

## Data type ownership

Each conceptual data category lives in exactly **one** layer. Cross-layer references flow downward through the public surface of the lower layer — `workflow` imports `workspace.Run` is fine; `workspace` importing `workflow.Workflow` is forbidden. For the full ownership table (concept → owning module) see `.claude/notes/architecture.md`.

**Pydantic vs plain class.** Pure data types (events, configs, results, lineage records, IR nodes) are `pydantic.BaseModel(frozen=True)`. Runtime containers carrying live instances (callables, asyncio objects, services) are plain Python classes with explicit `__init__`. `arbitrary_types_allowed=True` is **forbidden** in `src/molab/harness/agent/` — anything that needs it is a runtime container by definition.

## Key patterns

- **Topology-driven parallelism** — tasks grouped into levels by the dependency graph; same-level tasks run in parallel automatically.
- **Content-addressed caching** — `cache_key = f(snapshot.key, inputs_hash)` where `snapshot.key == f"{code_hash}:{config_hash}"` (`TaskSnapshot` — AST-normalized code + config; **inputs never fold into the snapshot**) and `inputs_hash` is owned by `Caching` (JSON-canonical over the task `inputs` channel: upstream outputs, sweep params, content-addressed `workdir` Path with stable Path serialization). Execution location is not task identity. Two sweep runs with different params never share a root-task cache entry. Auto-backed by `<workspace>/.molab/cache/<run-path>/`, never inside a scientific directory and never `~/.molab/cache/`. Locked by `tests/test_workflow/test_cache_contract.py`.
- **Atomic persistence** — all JSON writes use temp-file + `os.rename`; workflow-layer writes go through `workspace.atomic_write_json`.
- **Values-on-edges lowering** — the workflow DAG is lowered to a frozen molab-owned `ExecutionPlan` (`workflow/_engine/plan.py`) executed by the structural engine (`engine.py` `run_plan`): each task's inputs are delivered from its upstreams' outputs (declared `depends_on` wins; trigger-carried values reach dep-less targets — the loop-back/branch-routed input channel), a task launches exactly when its dependencies are satisfied, and deadlock is detected structurally (`WorkflowDeadlockError`, zero timing constants). The engine is fully self-owned: the pydantic-graph dependency was removed, `End` is molab's own sentinel (`workflow/types.py`), and no `src/` module may import `pydantic_graph` (full-src AST scan in `tests/test_workflow/test_engine_boundary.py`). A parallel-join and a loop-`until` cannot be fused onto the same task — use separate tasks.
